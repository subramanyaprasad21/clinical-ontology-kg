# Scientific and semantic audit

> Historical baseline audit, before the export/validation fix. Its findings and ratings are preserved. See [the follow-up](EXPORT_VALIDATION_FOLLOWUP.md) for current results. Baseline machine evidence is in `credibility_audit/pre_export_fix/`; the main evidence files now describe the latest run.

Checks executed 15 September 2026; documentation completed 16 September 2026. Audited baseline: `4f44c9f`. This review evaluates the existing T2DM project; it adds no biomedical data or clinical edges. The separate verification code was written and run by the same AI assistant that helped implement the project. “Independent” below means independent of production extraction/build helpers, not an external researcher or a second reasoning engine.

**Verdict:** the project is defensible as a small semantic integration prototype with a useful negative feasibility result. It is not evidence of a comprehensive diabetes graph, sophisticated clinical reasoning, independent biological corroboration, or unaided human ontology authorship. It is suitable for a supervisor discussion if those boundaries are stated and the author can explain the modelling decisions.

## Discrepancies and qualifications

These findings have not been silently repaired in the ontology or canonical graph.

1. **The original repeatability check was not a clean build.** `scripts/check_reproducibility.py` reruns into the same output directory. The new `audit/clean_builds.py` starts with no interim/processed outputs and confirms the stronger clean-output claim. It still uses the same installed environment and hard-linked frozen inputs. No fresh package installation, different machine or input reacquisition was tested.
2. **The completion language was too broad.** “Core complete” describes implementation of a bounded prototype. Three clinical questions remain unsupported. The full Mondo/HPO OWL theories were not imported, and clinical completeness was never tested.
3. **The original provenance percentage checked structure, not raw fidelity.** This audit also checked the 38 record locators and selected fields against raw files. All match. Of the 179 assertion occurrences, 62 are direct triples from the selected raw OWL class fragments; 117 are RDF projections of source information, including Parquet/HPOA relations and local concept types. The current graph does not attach a separate direct-versus-transformed flag to each assertion. Neither category means independent clinical confirmation.
4. **Query status is hard-coded.** The pipeline assigns unsupported status to questions 04–06 by filename and answered to the others. Those labels are not evidence of adequacy. The interpretation below marks four questions partially answered; the original machine outputs are retained unchanged.
5. **Two SHACL coverage probes passed despite questionable content.** A literal object on `kg:hasHPOAnnotation` is not covered by a relationship shape. A positive and excluded association for the same disease/term is not flagged as a conflict. Both were tested in isolated copies. Neither occurs in the canonical data. Conflict detection would need to preserve source context rather than automatically reject legitimate disagreement between sources.
6. **The invalid-case summary omits focus nodes.** Production code chooses an arbitrary matching entity/statement using graph iteration and records only violation counts. Counts repeat, but that is weaker than repeating a named fixture. The audit uses fixed, sorted choices and records actual focus nodes, paths, messages and components.
7. **OWL/RDF compatibility is not OWL DL certification.** Native class IRIs also represent terminology concepts. The builder replaces restriction/list blank nodes with named project IRIs. RDF round trips and the selected OWL RL rules work; this is not a test of OWL 2 DL profile validity or Protégé reasoner compatibility. No actual Protégé session has been verified.
8. **The drug/target absence conclusion was partly encoded in the audit program.** The original program writes unsupported messages after inspecting schemas; it is not a general relation-discovery engine. This review checked the actual catalog schemas and the inventory separately. The negative conclusion is justified for structured joins in these files, not for all possible information in free text or other Open Targets products.
9. **Authorship needs a precise boundary.** The author supplied the research direction and source/scope constraints. AI assistance also drafted the implemented OWL vocabulary and modelling choices. There is no recorded author sign-off of every axiom. A coding-only disclosure would be inaccurate for the present history.

## T2DM trace and verified join keys

Mondo contains `MONDO:0005148`, label “type 2 diabetes mellitus”, with named parent `MONDO:0005015` (“diabetes mellitus”). The 16 additional classes include disease and BFO upper-level context; they are not 16 T2DM-specific diseases. Exact synonyms and xrefs are preserved as source content, not proof of extra clinical facts.

The explicit Mondo mapping to `https://omim.org/entry/125853` connects HPOA `database_id=OMIM:125853`. Five annotations reference that ID with `TAS` and `OMIM:125853`. Their HPO terms are insulin resistance, Type II diabetes mellitus, increased waist-to-hip ratio, autosomal dominant inheritance and late onset. The latter two are separate I/C aspects. The HPO disease-like label is not equated to Mondo by name.

OT disease `id=MONDO_0005148` has the same full `code` IRI and parent. Five OT phenotype rows each have two duplicate evidence occurrences with `resource=HPO`. The term/aspect/evidence/reference/disease-ID/curation signatures match HPOA. Thus agreement across these deliveries is not independent corroboration.

## Semantic classification of the model

| Relationship or construct | Actual category | Interpretation and risk |
|---|---|---|
| Mondo named `rdfs:subClassOf` | Direct source RDF | Class extension inclusion; bounded named-parent projection only |
| OT `parents` → `rdfs:subClassOf` | Transformed source information | OT parent identifier is expressed as a class hierarchy edge; verified here against Mondo |
| Local concept types and schema subclass axioms | Authored modelling/projection | Not literal source assertions that the project classes exist in Mondo |
| HPO P/I/C predicates | Transformed source information | Annotation relations between terminology concepts, not patient-level facts |
| `hasExcludedPhenotype` | Authored vocabulary; exercised in tests | An exclusion marker, not an OWL negative-property assertion; no canonical instance |
| Mondo SKOS exact mappings | Direct source RDF | Preserve the source's alignment claim, not universal individual identity |
| Broad/narrow/related/close mappings | Allowed vocabulary/shapes only | No canonical mappings of these types |
| `owl:sameAs` | Inferred reflexive bookkeeping only | No source identity merge and no nonreflexive inferred identity merge |
| `owl:equivalentClass` | Authored local definition | Defines `PhenotypeAnnotatedConcept`; does not equate Mondo with OMIM or HPO |
| Domain/range | Authored inference axioms | Infer terminology types from relations; they do not reject malformed records |
| Existential/intersection restriction | Authored inference axiom | Positive annotation to an HPOTerm suffices for the defined concept class |
| Mondo nested restrictions | Retained raw/audit evidence, not executed | Cannot claim source clinical restrictions were reasoned over |
| OWL cardinalities | Absent | No `owl:minCardinality`, `maxCardinality`, exact or qualified cardinality axioms |
| SHACL min/max counts | Authored validation rules | Required/single-valued fields; not OWL cardinality semantics |
| PROV and named graphs | Generated process/record metadata | File/record traceability; inference uses whole-input process lineage, not minimal proofs |
| Invalid examples | Synthetic, isolated test mutations | Not canonical biomedical knowledge |
| NANDO and clinical drug/target edges | Unresolved / unsupported | No stronger relationship is asserted |

For terminology-level mappings, the choice of SKOS is defensible. For class reasoning, the class/concept dual use must be explained explicitly. In particular, an association with the HPO term “Type II diabetes mellitus” and an inheritance annotation attached to a susceptibility record should not be restated as diagnostic criteria or universal inheritance of common T2DM.

The [OWL primer](https://www.w3.org/TR/owl2-primer/#Class_Hierarchies), [SKOS mapping definitions](https://www.w3.org/TR/skos-reference/#mapping), and [SHACL specification](https://www.w3.org/TR/shacl/) provide the language definitions; the evidence for this project's claims is its local data and code. OWL domain/range supports entailment, whereas SHACL checks a selected graph against shapes. Exact matching does not license unrestricted substitution of facts between concepts.

## What reasoning added

The reasoner is `owlrl` 7.6.2 with `OWLRL_Semantics`. It runs on source facts plus the local schema, without source imports or provenance. This audit reproduced the exact standard-RDF closure delta: 585 triples. The 84 internal generalized-RDF triples excluded from export are bookkeeping with literal subjects, not additional clinical findings.

| Asserted facts | Local axiom/rule | New fact verified |
|---|---|---|
| Mondo T2DM `a DiseaseConcept`; `hasPhenotype HP_0000855`; HP term `a HPOTerm` | Equivalent intersection/existential definition | T2DM `a PhenotypeAnnotatedConcept` |
| Equivalent positive facts for OMIM:125853 | Same definition | OMIM concept `a PhenotypeAnnotatedConcept` |
| T2DM `hasPhenotype HP_0000855` | `hasPhenotype owl:inverseOf phenotypeOf` | HP term `phenotypeOf` T2DM |
| T2DM subclass diabetes; diabetes subclass its named parent, continuing along raw edges | Subclass transitivity | Fifteen additional named ancestors of T2DM beyond its direct parent |

There are two concept classifications, six inverse relations across the two disease identifiers, and fifteen selected ancestor inferences: 23 examples. The original inference competency query returns 22 because it selects the Mondo classification but not OMIM's. Every example is absent from asserted premises. The detailed audit records a source edge path for every ancestor. Removing all positive phenotype facts from real premises removes both classifications and all inverse phenotype facts.

These are genuine but elementary inferences. The local definition was chosen to demonstrate a reasoner; it does not discover a new clinical category. Because domain/range already supplies the concept types, the existential classification is largely a test for the presence of a positive annotation. SPARQL question 01 independently traverses asserted subclass edges; that traversal is not the OWL reasoning result. No treatment classification is demonstrated.

## Provenance and reproduction risks

Required recorded fields are present for all 179 assertion occurrences, covering all 174 source quads (100%). All 38 selected-field source payloads/identifiers match raw records. Direct source mappings also have their extraction record and mapping method. The graph uses RDF reification and PROV-O, not RDF-star.

Remaining limits: source versions for OT are declarations; the manifest cannot reconstruct download receipts. A build ID is a deterministic transformation identity rather than a wall-clock execution record. Inference links to the entire premise set; minimal proof provenance is supplied only in the new selected examples. Class-record provenance does not retain every source OWL axiom annotation.

Two clean output builds with Python 3.12.7 and the pinned packages were byte-identical, including the final report. This is stronger than merely comparing graph isomorphism, but weaker than reproducing from an independently installed environment or public downloads. Raw inputs are excluded from Git, so a recipient needs the exact files separately. The manifest has hashes, not a working acquisition recipe. No network blocking monitor was used during the run; offline behaviour was checked by code inspection and local input use.

## Presentation and authorship

The first README led with completion and technology claims, repeated caveats, and linked to many locally generated files absent from Git. Empty scaffold directories and implementation notes also made the entry point look more administrative than necessary. The revised README follows the direct problem/result style of the author's FACT sample, as also used in the Transformation Fidelity project. No scientific content was copied from that unrelated study. Detailed limitations and audit evidence remain available rather than being deleted for appearance.

A short disclosure identifies AI-assisted code, debugging, documentation and OWL drafting. The [design decision record](../docs/DESIGN_DECISIONS.md) separates scope decisions supplied by the author from implementation choices awaiting author review. Review and revision can establish a defensible author-approved design; it cannot retroactively make generated design unaided.

The Git history begins with the already-completed local core and then records the audit and documentation work. It does not backdate work or reconstruct fictitious daily progress. The remote is private. Public distribution and source licensing review have not been completed.

## Before showing a supervisor

1. Work through the design decisions and the [defence guide](../docs/SUPERVISOR_DEFENCE_GUIDE.md). Explain each axiom and reject or revise choices you do not accept. Record the actual review date and reasons.
2. Perform the [Protégé review](../docs/PROTEGE_REVIEW_GUIDE.md), particularly the class/concept distinction and named restriction export. Do not claim a successful DL reasoner run until it is observed.
3. State the shared evidence lineage and absent clinical drug/target data in the first discussion. Present the project as an engineering case study, not a new biomedical discovery.
4. Before claiming portable independent reproduction, recover source acquisition records or agree a lawful way to provide the exact raw inputs. A private Git repository alone does not solve this.
5. Before extending validation coverage, decide what source disagreements mean. Add a generic-annotation endpoint shape and context-aware positive/excluded conflict check only as explicit, tested design changes. They are not silently added by this audit.
